## Independently reproducible software risk

Original `to_thread` awaits are cancelable, but a running decoder/constructor
thread continues. Fake-worker tests on the exact base reproduced:

* canceled wake decoding overlapping the next foreground decode;
* cancellation during cold loading allowing another constructor, abandoning the
  first constructed model;
* a new decode executing while the previous abandoned worker was active.

Three of the initial four ownership tests fail on the original source; the
constructor failure/retry test already passes. This demonstrates orchestration
risk with fake workers. It does not establish that actual CTranslate2 execution
overlaps internally, that a live timeout occurred, or that this caused the three
observed empty recognitions.

## Focused candidate behavior

One owned worker per transcriber holds an async permit across the existing native
thread execution. Cancellation returns to the caller without stopping the thread,
but its owner retains the permit until actual completion. Work canceled while
waiting for the permit is canceled and drained without ever executing. A strong
reference set is emptied by completion callbacks; abandoned results/exceptions
are consumed without logging or enqueueing them.

Cold initialization has a shared owned task. Caller cancellation cannot discard
its cached result or initiate a duplicate constructor; failure still permits a
later retry. Wake and foreground decoding use the same permit. Recognition
arguments, PCM preparation, client messages, 60-second foreground timeout and
privacy-safe diagnostic fields are unchanged. Queue wait is observable through
the existing `worker_wait` phase.

Python 3.14's `asyncio.shield` explicitly calls the loop exception handler for a
late failure after its waiter is canceled, even when another callback retrieves
that exception. An intermediate candidate exposed this in a stress test. The
final implementation uses `asyncio.wait` on owned tasks, which does not cancel
children or implicitly log their late exception; it propagates results/errors
only to active waiters. No exception-handler suppression or global loop changes
are made.

Limits: this serializes calls that could previously overlap. A genuinely hung
native call retains the permit, so later foreground calls reach their existing
deadline rather than spawning more workers. It does not implement process-level
termination, automatic restart, or a wake-specific deadline. Process/event-loop
shutdown and real decoder throughput remain untested. No live installation or
recognition-quality improvement is claimed.

## Remaining capture delays

The meter still uses the reviewed zero display-lock wait. Network operations
remain synchronous in the microphone task: its send mutex, WebSocket TX mutex
and transport writes can each wait against 1000 ms active/2000 ms wake timeouts;
error paths can also wait for another client mutex. Wake/start/end controls and
logging introduce other waits. These greatly exceed the approximately 50–60 ms
RX DMA buffering span, establishing possible loss/backpressure mechanisms.

Existing `capture_gaps` measures application service timestamps, not RX sample
continuity or stage ownership. No new stage timing/RX-overflow observation was
collected here. A queue/epoch/control redesign or shorter send timeout would
change buffering/drop behavior without attributing residual observed gaps; no
firmware fix is proposed as proven. Stage/overflow instrumentation could be
reviewed and observed later without speech, but requires separate live firmware
work. Actual intelligibility, wake accuracy, empty-result cause, double-talk and
echo suppression still require a controlled physical speech test.

## Independent lifecycle review

Two additional synthetic tests characterize shutdown and blocked-worker limits.
Repeated caller timeouts retain one active native owner and discard all queued
work. Direct cancellation of that owner (as during global event-loop teardown)
releases its asyncio lock even though the native thread remains alive. This is
an explicitly reproduced limitation, not a shutdown fix. The provider has no
close hook, no native execution deadline and no provider-level admission cap;
the socket connection cap and foreground deadlines bound ordinary callers only.
A permanently hung native call can delay default-executor process teardown.
Do not claim bounded shutdown or reuse the provider after globally canceling its
owners. No subprocess process-exit test or real native throughput test was run.

The independent review found no ordinary caller-cancellation race. Existing wake
exception-text logging is outside this patch and remains a privacy concern.
The final aggregate suite contains 373 passing tests, including the two added
lifecycle characterizations. Deployment of this backend-only candidate would
require backend source replacement and a service restart; no firmware change.
