# Friday: one context-aware assistant that completes a bounded Mac task

Design proposal. The direction is Jarvis-like continuity and competent task completion across Mac, phone and device. This is product context, not permission for unrestricted machine access or a claim of consciousness.

Publication base: remote main `29c48ec`. The task prototype is standalone and does not import production app startup. Earlier development-source inspection informed the adapter map below; later Calendar/Weather/continuity features and installed firmware repairs are not dependencies or included changes. Treat the map as architecture context, not a claim that every referenced adapter exists or is deployed on this PR base.

## The product beyond the first proof

Friday should be continuously available, context-aware and effective at carrying goals through, across phone, Mac and the physical device. The project repair is the first trusted fixed-fixture execution proof, not a coding-only product. The eventual domain adapters can support meeting preparation, personal organization and explicitly approved Mac workflows through the same task/context/authority model. Presence means consistent task awareness and helpful timing, not watching every application or claiming knowledge without evidence.

Introduce a ContextBroker over approved adapters, alongside TaskStore. Each fact/reference records owner, source adapter, source object ID/revision, observed_at, valid_until, permission/data-sharing scope, sensitivity, provenance and whether it is observed, user-stated or inferred. Separate transient working context, durable task checkpoints and explicitly approved personal memory. Resolve “that meeting,” “the failing check,” “what I asked you yesterday” against fresh scoped references or ask. An explicit correction increments context revision and invalidates dependent plans/approvals; retain successful public observations only until their stated expiry. Preserve full fact before memory confirmation. Source permissions are checked at acquisition and again before use/display/model sharing; local visibility never automatically means paid-provider disclosure.

Current usable sources: user speech/text and selected touch actions; explicit stored memories and bounded conversation history; authorized Calendar events with existing calendar_model_context policy; configured-ZIP Weather with observed expiry/source identity; reminders and their exact IDs; opt-in existing Spotify playback state subject to current privacy/access flags; task/check evidence once the runner is built. These are bounded knowledge, not an all-knowing profile. Calendar/Weather reference code already provides a narrow working example. Selected-project files and check outputs are a proposed adapter, not currently accessible through Friday tools. Foreground app/window/selected document, email/messages, filesystem-wide indexing, browsing history, camera/location and new account services are future sources requiring specific user authorization and implementation; none should be collected for this first proof. No generic background scraping or hidden retention.

Uncertainty is part of competence: “Calendar says14:00, last checked10minutes ago” when freshness matters; “I can't tell whether that input was intelligible speech” for the VAD metrics; “The check passed, but this behavior wasn't exercised” for incomplete validation. A model suggestion is an inference, not a tool observation or memory fact. Where sources conflict, retain provenance and ask about the decision that matters instead of silently selecting a convenient answer. A dismissed/expired private reference must not reappear through a conversation summary, another client or proactive notification.

Selective proactivity comes from an explicit user goal/subscription and fresh events: alert a user-requested reminder, notify that a requested task completed or is blocked, offer meeting prep when the user enables that behavior, or flag a material context change that invalidates the task. Existing ReminderScheduler is a narrow implemented scheduled example; a general event/context policy service is proposed. Add deduplication, urgency/quiet-hour preferences, expiry, notification budget and an owner-level dismissal ledger across clients. Default to silent context updates; interrupt only for a meaningful authorized reason and show the reason. Do not wake/speak repeatedly, expose private details on a locked phone/LCD, or manufacture “thoughts” to imply sentience. Respect protected reviews and current conversation; completion can be a subtle ambient cue with a concise phone result until the user opens it.

Presence follows the same authoritative facts on all surfaces. Mac is the first execution host; phone is authenticated remote control/review; ESP32 is ambient voice/touch presentation. A device-specific animation or a phone's local connection state cannot assert task completion. Offline/permission-revoked sources show unavailable/stale explicitly. A new conversation can coexist with a task under execution without wiping it; task focus and a small “still working on…” reference keep continuity. Durable bounded checkpoints let Friday recover after reconnect/restart, while a verified Stop and visible limits keep agency predictable.

Second end-to-end acceptance after the runner/context core: **“Help me prepare for my next meeting; keep the prep reminder tied to that meeting.”** With the user's existing authorized Calendar, resolve the exact event and ambiguities, record a temporary event/task reference, draft a preparation checklist using only permitted source context, propose an exact reminder time, obtain applicable explicit confirmation, and persist the reminder's identity. Later, from phone: “Move that prep reminder ten minutes later.” Resolve the same owned reminder/event, check for a changed Calendar time and approval revision, show the exact change, execute through the existing idempotent reminder adapter, verify the stored result and show/speak one coherent update on the device. If source sharing is not permitted, use local/deterministic handling or explain the limitation; do not send the event to a provider. This tests useful personal context/action continuity beyond coding without adding email, travel booking, unrelated account access or omniscience claims. The existing adapters cover pieces; durable task linking/cross-client scope and this complete acceptance are not implemented yet.

Every later domain must plug into the same plan/execute/verify/recover contract with typed operations, scoped grants and evidence. Avoid a broad executor built before narrow proofs; also avoid leaving each domain as an isolated chatbot response. Shared task/context state and independently verified adapters provide the path from the first project task to the wider assistant.

## The first real task

User selects one small project on their Mac and says: **“Friday, investigate this project's failing checks. Prepare a fix and show me what changed.”** Friday asks only for the missing project or check choice, retains that choice, inspects it, makes an isolated working copy, runs the explicitly approved established offline checks, identifies an observed failure, proposes and prepares a narrow patch, reruns the failing check and relevant suite, and returns the patch plus evidence. It stops before modifying the original checkout, committing, publishing, deployment or dependency installation. If checks already pass, it reports that evidence rather than inventing a fix. If diagnosis is uncertain, it presents the failing evidence and asks one specific question.

Choose an actual user-selected Python project with a known existing local interpreter and unittest/test command for the first acceptance run. A repository with pure local tests and one bounded reproducible failure is suitable. Projects requiring downloads, production credentials, integration endpoints or destructive check scripts are unsuitable for the first run; explain the blocker instead of substituting an unrelated repository. An original synthetic fixture can validate failure/recovery mechanics offline first, but does not count as the useful real-project acceptance task or proof of model reasoning.

Expected device conversation: “I found the failing check. I'm isolating a fix.” User: “What are you changing?” Friday answers from the same task's patch facts without restarting the task. User: “Keep it as a patch.” Friday records that scope correction. The ambient orb shifts to a compact work scene with current phase, one factual update, and persistent Stop/Review controls; there is no new app grid or permanent dashboard. Completion: “The failing check and the local suite now pass in the isolated copy. The patch is ready for review.” Only say this when saved check results support it.

## Smallest architecture addition

Keep one FridayAgent as the conversational coordinator. Add a **separate durable TaskStore/TaskWorker** for long work and a narrow ProjectRunner service interface on the same Mac. A small task-start adapter can enqueue it from a conversational turn. Do not stretch the existing120s/five-minute conversational queue into an unbounded executor or make the LCD host execution. ProjectRunner exposes typed operations, never a model-supplied shell command.

TaskStore schema proposal: tasks(task_id, owner_id, machine_id, project_id, goal, scope_revision, plan_revision, state, cancellation_generation, timestamps); steps(task_id, step_id, kind, input_hash, state, attempt, lease_owner, fencing_token, started/completed times, evidence_ref); approvals(owner/task/machine/project, scope digest, plan revision, expiry, permitted operations); task_events(monotonic task revision, event type, safe summary, artifact ref); artifacts(hash, relative path, source/check revision, privacy). Store a minimal bounded task context: selected project, original commit/tree digest, approved check definitions, current step, diagnostics references, patch digest, successful/failed checks and unresolved question. No raw credentials or arbitrary full environment. Task artifacts have retention/deletion controls and are not automatically promoted to personal memory.

Task states: proposed → awaiting_scope → queued → inspecting → checking → diagnosing → preparing_patch → verifying → ready_for_review. Side states: awaiting_clarification, awaiting_approval, stopping/stopped, recovering, failed. “Ready for review” is a terminal result for this scope; applying the patch is a later separately authorized task. Store facts/checkpoints after each step. Enforce transitions with compare-and-swap revision/fencing tokens. Persist leases/heartbeats; one active owner per task/project avoids duplicate writes. A lease expiration triggers reconciliation, not blind rerun of an uncertain operation.

Typed first-slice operations: inspect_project_manifest(project_id), create_isolated_copy(task_id, source_digest), read_project_files(relative_paths), run_approved_check(check_id, source_digest), prepare_patch(base_digest, edits), verify_patch(check_ids), export_review_bundle. Resolve real paths against the selected-root grant; reject symlink/traversal escapes and nested alternate roots. Source text, AGENTS/README and command output are evidence/instructions for the selected task, never permission to expand machine capabilities. Check definitions must be reviewed and bound to exact executable argv, cwd, environment and script/tree digest before execution.

Isolation includes original-checkout preservation, dependency availability and allowed writes, not just a Git worktree label. Worktrees can share .git and hooks/config; do not run hooks or permit writes to the original repository metadata. Prefer a detached isolated copy with private Git metadata for the first slice unless worktree enforcement is proved. Handle dirty/untracked source explicitly: capture an immutable snapshot or ask which state is intended; never reset or stash the user's changes. No shell interpolation. No inherited service credentials or API keys. Never install dependencies automatically.

**Execution containment is a release gate:** repository tests run code and can spawn children, access files or network. An argv allowlist, copied checkout and sanitized environment alone do not enforce isolation. Before enabling real selected-project checks, prove an available OS-enforced runner can restrict reads/writes to granted project/runtime paths, deny network by default, exclude credentials, bound CPU/time/output, and terminate the entire owned process tree including detached children. This codebase has no such runner today. Spike this capability without installing software or altering permissions; if unavailable, report the exact blocker and request separate approval for the proposed runtime/setup. Do not ship a weak subprocess wrapper as a secure sandbox. A preflight with adversarial fixture tests must demonstrate containment before running unknown project scripts.

## Shared context and interruption

Task identity persists across turns/reconnects and maps to an account/paired owner and selected Mac; turn request IDs remain presentation identities. Device and speech focus the same task_id/context_revision. “That failure,” “keep it local,” “what changed?” and “resume it” resolve from task evidence; ambiguous references ask which task/project. Do not guess from an expired Calendar view or last assistant sentence. Other authenticated displays receive only task information authorized for that owner; private files stay in Mac review artifacts, while LCD/spoken status uses short safe summaries.

Use existing experience envelopes for a task scene: task_id, task_revision, phase, concise observed status, current step, task action tokens and bounded evidence refs. Native UI does not accept arbitrary HTML/paths or raw terminal output. Reuse rounded scenes/attention/recovery, existing glyph sanitation and media/memory priority. A reminder or full memory review can cover the task scene without stopping task execution or implying approval; return to latest task state afterwards. Dismiss hides a scene only. A new request can interrupt narration or ask a task question without replacing the task plan. Changing project, output scope or commands increments scope/plan revisions and pauses affected steps until authorization is valid again. Model-produced plans can propose scope; only deterministic policy/approved grants admit operations.

Clarification and approval are durable waits, not worker timeouts. Bind replies/buttons to task, owner, revision and single-use action ID. A delayed “yes” for an earlier plan cannot authorize the revised plan. Preserve sequential memory review unchanged; task review must never consume its consent. If the model/provider fails, persist the last verified step and explain the actual limitation without fabricating progress.

## Reliable Stop and recovery

Add an owner-bound, idempotent cancel(task_id) route independent of the model and ordinary job queue. Persist cancellation_generation immediately and acknowledge “Stopping,” not “Stopped.” Runner checks it before every operation and before publishing/committing any output; cancellation revokes outstanding execution grants. Terminate active work with a bounded graceful interval then an enforced process-tree kill. Persist final evidence that children are gone; only then report Stopped. If unable to prove termination, report stop_failed and keep further operations fenced. Give the native task scene a persistent48px+ Stop control, accessible from the ambient task indicator and protected overlays without approving/dismissing their contents; provide a Mac-local stop fallback when the device is offline. Spoken “stop this task” uses the same deterministic route, but unreliable speech must not be the sole stop path.

Stop during a model request cancels delivery/planning and prevents late output from admitting a new action. Stop during patch writing leaves either atomic validated files in the isolated copy or an explicit incomplete artifact, never a claimed successful patch. Stop/restart/reconnect does not auto-resume writes. On recovery, reconcile process liveness, completed check evidence, source hashes and patch state; ask before resuming an uncertain mutation. Preserve the original checkout and prepared artifacts; delete only task-owned temporary paths under an explicit cleanup policy.

Duplicate start/action IDs return the existing result; cross-owner conflicts reject. Old task revisions and other-peer action tokens reject. Delivery retries reuse evidence/results rather than rerunning checks or edits. Late model/check outputs must match task, lease/fencing token, cancellation generation and source digest before affecting authoritative state. Keep the installed rejected-mutation latch fix and add task-specific rejection/stop tests; never weaken privacy or consent guards to make navigation responsive.

## Evidence and end-to-end acceptance

A completed review bundle contains initial source digest, approved command manifest, before failure/check exit status and bounded diagnostic references, proposed explanation, exact patch/hash, affected files, after check exits, broader suite result, limitations and artifact links. Bind all successful checks to the final isolated tree digest. If code changes after checking, invalidate evidence and recheck. Exit0 is necessary but not proof the requested behavior works; add the targeted meaningful regression and human-readable observed before/after. Model text is never execution evidence. Redact credentials and sensitive source from operational logs; retain protected raw artifacts locally only as approved.

Acceptance on one genuinely selected project: (1) user grants project/check/scratch scope, (2) Friday observes the real failure, (3) user asks “what failed?” mid-task and gets current evidence, (4) it produces a narrow fix without changing the original, (5) failing regression plus established local suite pass, (6) correction “patch only” remains honored, (7) device reconnect recovers the same task without rerunning side effects, (8) Stop during a running check kills all owned processes and prevents subsequent steps, (9) explicit resume reconciles evidence, (10) duplicate/stale/other-peer approvals cannot execute, (11) final review bundle proves final-tree checks, and (12) no commit/push/deploy/download/network occurred. A run that cannot diagnose a failure should honestly return failure evidence, not claim the acceptance goal complete.

## Phone control: the same assistant, not a second bot

The phone must share the same Friday owner, explicit memory, conversation and durable tasks. It can initiate the selected-project task, inspect progress/artifacts, answer a task clarification, approve an exact scoped operation, and invoke deterministic Stop. Away-from-home use is a requirement, but no public port, tunnel, token, messaging account or OS permission is authorized by this design request.

| Option | Fit with inspected code | Additional work / limits |
|---|---|---|
| Authenticated mobile web client | Existing static app.js/index.html and FastAPI/WebSocket stack offer text input, surfaces, actions, reconnect and result ACKs; good basis for task progress, diffs and exact approval review | Current app is a device simulator with an in-memory device token; it is not a phone account/login or remote task client. It does not advertise experience_context_v1. Needs responsive task views, owner auth/sessions, task APIs/event replay, CSRF/origin protection and remote connectivity. |
| Messaging adapter | Conversational input/results can map to the same task service; familiar remote notifications | The production baseline has no messaging account binding; this PR adds a disconnected Telegram prototype, not a live integration. Requires third-party account/bot/webhook credentials, verified sender-to-owner mapping, duplicate webhook handling and provider-policy/data-sharing review. Long patch/permission review and reliable Stop require links to a richer client anyway. Message delivery is not execution evidence or consent. |

**Telegram is the current first phone transport.** The mobile web harness remains offline test evidence and a possible richer review client. Both share task ownership, scope and Stop; neither is a separate memory or executor. Do not expose simulator/admin APIs or reuse the ESP device token as a phone credential. Live enrollment, privacy acceptance and remote access remain unbuilt.

Existing memory/history/working context are scoped by device/session ID, DeviceCredentialStore stores one hashed token per device_id, and DeviceHub gives up to4 peers per device ephemeral peer keys. These do not implement one human account with independently revocable phone clients. Introduce Owner/Client registration with explicit pairing enrollment, per-client identity and revocation plus stable owner-to-existing-device mapping. Keep existing memories in place through a reviewed ownership mapping rather than copying private records between guessed users. User chooses which existing Friday identity the phone joins. Do not rotate/reuse the physical device token to enroll a phone. New phone credentials/sessions require explicit setup approval.

Phone login should use an approved authentication flow with short-lived secure HttpOnly/SameSite sessions (or equivalent reviewed client credentials), TLS, CSRF protection on mutations, WebSocket origin/session validation, request limits and idle/session expiry. Authentication and scoped execution approval are separate: logging in does not authorize arbitrary Mac access. Require recent authentication for scope expansion and show the full action/project/command/write/network/cost scope before approval. Artifact access checks owner/task authorization on every fetch; private source is not served by public static paths or printed into device status. No bearer tokens in URLs, localStorage, logs or messaging payloads.

Task focus is owner-scoped while each client retains independent browsing/presentation state. Phone task progress and spoken/device status derive from the same stored task revision. A phone question does not steal the LCD's protected review or invalidate an executing task. Reuse request/epoch/sequence guards per client, but publish authorized safe task summaries through a separate task subscription/snapshot protocol; existing source-peer presentation filters deliberately suppress another peer's private replies and must not be globally relaxed. A task review can be explicitly opened on either client under a review revision/lease. Client takeover invalidates earlier action tokens without implying consent. Keep the memory full-fact sequential review invariant; do not silently mark pages reviewed because the phone opened a link.

Approvals bind owner, client authentication, task/machine/project, exact scope/plan revision and digest, expiry and one-use action nonce. Store acceptance atomically with transition admission; duplicate phone/device taps return the same decision and cannot execute twice. Request IDs plus task step idempotency/fencing protect execution. Revocation closes active subscriptions, invalidates sessions/unconsumed approvals and rejects new actions. Active operations must observe revoked execution authority at the next bounded fence; provide an explicit revoke-and-stop action, with the same verified termination semantics. Do not revoke the physical device merely because the phone is lost.

Remote connectivity is a separate setup choice: prefer an authenticated private connection to the Mac, rather than exposing the backend/LAN publicly. First determine whether an already approved private route exists; none was established in this pass. A private overlay/VPN or outbound authenticated relay would need installation/account/configuration approval if absent. A relay entails its own authentication, storage, metadata/cost and availability design; it must not turn forwarded traffic into loopback admin authority. Do not trust arbitrary forwarded headers or change loopback-only API protections. The minimal first client can support away-from-home when phone and Mac are online on the approved private route. Mac sleep/offline availability must be explicit; changing sleep settings or adding an always-on cloud control plane is separate scope.

Offline phone displays last-known state with timestamp and a clear disconnected indicator. It must not show local optimistic “Approved,” “Running” or “Stopped” as server-confirmed. Queue no automatic approvals or new executions for replay after reconnect; obtain a fresh task snapshot and require a still-valid exact review. A duplicate reconnect/start uses the same task/action ID. Stop with no server ACK remains “Stop not confirmed”; retry only the same idempotent stop request after reauthentication/reconnect and never claim processes are gone. A long-running task may continue only within its existing bounded grant; Mac sleep/restart recovery rechecks expiry, process state and source evidence. Optional notifications/push subscriptions are later explicit permissions, not assumed.

Add acceptance coverage: start on phone, query the same task by speech, answer clarification on device, review the exact patch on phone, race duplicate approve/stop taps across clients, revoke only the phone, reconnect after offline/sleep, and verify no stale action/duplicate execution/private cross-owner artifact leak. Browser behavior and phone touch/viewport/accessibility checks supplement actual native720x720 tests; they do not replace native device proof. No phone account, connection, credential, external integration or remote endpoint was created here.

## Decisions and permissions still needed

For phone setup, later choose which existing Friday owner to enroll and approve a concrete private remote-access/authentication setup; no such changes are authorized now. For design, none: recommend patch-only scope, offline checks, network denied, original checkout unchanged, one project/task at a time. Before the real acceptance run the user must choose **the project and intended source state**, approve the exact existing checks/scratch write scope, and choose **existing local inference or a separately approved paid-provider budget/source-sharing policy**. Do not ask for generic “full Mac access.” Start with a proposed bounded30minute task,10check invocations, one check process at a time and bounded artifact/output retention; expose actual limits in the concrete scope review and ask only if the chosen project exceeds them.

This slice needs no Accessibility, Screen Recording, Full Disk Access, global Automation, cloud-account integration or new credentials. Standard selected-project filesystem/process rights still need a concrete user grant and proven containment. Protected/unknown filesystem locations, additional runtime installation, network/dependency access, external source sharing/paid API calls, broader GUI/Apple Events control, persistent background grants, changes to original files, commit/push/merge/deploy or firmware/service installation each require separate explicit scope approval. Existing model keys/account access do not approve new costs or sending project source. Keep all those capabilities absent until needed.

The result should feel like one competent assistant: it remembers what it is doing, notices a real blocker, explains the next useful choice and finishes with checked evidence. Personality and coherent motion support that behavior; another scene or a larger prompt cannot substitute for it.
