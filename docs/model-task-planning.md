# Disconnected provider-based task planning

TaskPlanner defaults to disabled. It accepts an injected TextProvider or existing ProviderRouter, with no provider construction, credential reading or network request on its own. Tests inject providers or mock the existing router selection; no real provider inference has occurred. An absent provider fails explicitly and never falls back while pretending a model reasoned.

The provider receives the original registered Python range fixture, bounded task goal and evidence references. Planning occurs only before task approval; ordinary fresh tasks therefore have no observed failing-test evidence yet. It is source-based repair inference, not a claim to diagnose a test already run. The arithmetic fixture regression uses the equivalent inclusive-range operation; the real local fixture uses the supplied Python source. Actual execution evidence remains the worker's responsibility.

The only accepted output is one propose_registered_plan tool call, no text, with inclusive-range-v1, all five existing operations in order and exactly the evidence references supplied. Extra fields, commands, paths, generated code, alternate repairs, fabricated references, skipped checks and result claims fail validation without changing task authority. The model can propose only the existing repair; this does not establish general model planning capability. A validated proposal adds provider/proposal metadata to the scope, increments plan revision and requires a fresh nonce/revision/digest approval. It never approves or runs a task. Existing executor capabilities, fixed command and fixed replacement bytes remain unchanged. Use the task read or Telegram /status to display the resulting model scope. An explicit /review refreshes approval while preserving planner metadata when source and executor are unchanged; changed source or executor invalidates that association.

SQLite stores plan identity, source/executor/revision/generation/admission snapshots and state. Duplicate requests do not reissue inference. Stop, review or source changes fence pending replies; the provider is cancelled best-effort and late responses cannot commit. The deadline is bounded to ten seconds and is configurable downward for tests. A provider ignoring cancellation can continue remotely; usage is not promised cancelled, and its late result has no execution authority. Startup recovery marks interrupted inference uncertain and never automatically repeats a potentially billed request. Recovery requires exclusive supervisor ownership and must not be called as a routine poll against a healthy worker. Explicit fresh attempts need a new action identity and user intent.

Tests cover off-default behavior, existing-router injection, exact validated proposal and stale approval, duplicate requests, malformed/fabricated/expanded responses, cancellation, task review during inference, deadline uncertainty, interrupted-inference recovery and unchanged local-executor capabilities. All results are from injected test providers, not model-quality or live-provider evaluations.

## Smallest separately authorized live evaluation

Select one existing configured provider/model through ProviderRouter and authorize one bounded inference using only this original synthetic fixture. Confirm the provider's existing secret is available through its normal protected configuration without exposing/copying it into evidence. Set a small explicit provider token/request budget, use the ten-second planning deadline, and allow outbound requests only to that provider. Test output normalization/tool-call compatibility for the selected adapter before calling it. Show and approve the resulting exact execution scope separately; inference permission never grants fixture execution permission. The disposable root/test command/repair remain unchanged. No personal history, user-selected project, arbitrary tool set or additional Mac permission is needed. Nothing here enables this evaluation, consumes a key or makes a live call.

The disconnected planner now runs SQLite admission, current-task reads, final proposal validation, and failure/cancellation recording through the store's cancellation-drained off-thread I/O helper. Waiting for a provider uses a task-change notification and the actual planning deadline, rather than querying storage every 10 milliseconds. The final synchronous transaction still checks revision, generation, source/executor identity, and its unique admission before saving a proposal. A blocked SQLite writer therefore delays a plan without blocking the async event loop. This changes scheduling; the accepted proposal remains the single registered repair and does not establish general model diagnosis or generated-patch capability.
