# Telegram first phone transport: offline slice

Telegram is now the preferred first phone transport; the existing mobile web harness remains test evidence. Both use the same TaskStore owner/task/conversation identity and approval/worker rules. `backend/app/task_telegram.py` has no dependency on Telegram libraries, token configuration, network requests, polling, webhook, production app, or real executor. Tests supply original synthetic Bot API-shaped updates directly. Operational and adversarial tests cover binding, private chats, ownership, exact-scope approval, expiry, duplicate deliveries, persistence across adapter recreation, Stop during a running worker, revocation and rebinding privacy.

Supported commands are `/help`, `/tasks`, bare `/stop` (only one unambiguous active task), `/fixture range-total`, `/fixture range-total-two`, `/status TASK_ID`, `/review TASK_ID`, `/ask TASK_ID QUESTION`, and `/stop TASK_ID`. Approval is an opaque callback token resolving to a stored task ID, revision, scope digest, nonce, expiry, verified user/chat and owner. The scope is shown in full as readable labelled prose before the button. Raw executor output is withheld by default; status uses step counts and exit summaries. Bound command errors and invalid/expired approvals return safe guidance, with callback acknowledgement attempts. Telegram callback contents cannot introduce a command or change the scope. Cached duplicate responses are checked against current access and owner binding before being returned. Neither display names nor arbitrary owner fields authorize access.

This adapter accepts trusted updates, not authenticated Internet requests. Bind, revoke, handling and delivery authorization share a per-database lock across adapter instances in one process. Persistent binding generations invalidate cached replies and outbound descriptors after access changes. Tests cover revocation during approval admission and rebinding during response preparation. A future sender must authorize the descriptor immediately before delivery; network delivery itself needs serialized access updates. It must run under one process/consumer/supervisor (the lock is not cross-process); The separate off-default task_telegram_transport module now implements durable offsets/outbox, chunking, callbacks and a supervised service loop with fake HTTP tests. Live authentication, protocol acceptance and production supervision remain unverified. Do not mount `handle` as a public endpoint. Numeric IDs in a caller-supplied JSON object alone provide no authenticity. No new live authentication capability is claimed. Bind/revoke operations are privileged local configuration methods, never chat commands. Revocation prevents new control/read requests; it does not cancel already approved work. Stop that work explicitly under the task supervisor when revoking execution authority. Ordinary cached updates/callbacks remain bounded; confirmed old transport groups can retire with persistent replay fencing, while pending/uncertain records remain protected. Stop bypasses ordinary admission caps. See telegram-transport-service.md for explicit reserved-space and backpressure behavior; this is still a prototype retention policy.

## Minimal separately authorized connection

1. Create or select a dedicated bot through Telegram's official setup and place its token in a protected local secret store. Never paste the token into chat, repository, logs or evidence. Nothing here has created a bot or obtained a token.
2. Configure the off-default fixed HTTPS connector and single polling/sending service in task_telegram_transport, after separately authorizing live access. It verifies TLS and persists offsets/retries/outbox state. No real service was started or connected here; it requires no inbound port. Do not combine polling with an active webhook.
3. Verify the person's numeric Telegram user ID and private chat ID through an out-of-band trusted pairing flow, then bind those IDs to the existing Friday owner locally. Unknown users, groups, channels, bot senders and inline callbacks without the bound private message must remain denied. Never infer identity from usernames.
4. The disconnected service sends plain text with previews disabled, splits long replies, durably confirms full scope before keyboard/approval admission, acknowledges callbacks and records outgoing delivery progress. Verify these behaviors on the authorized live bot; uncertain sends are withheld rather than blindly repeated. Tokens belong only to the bound chat, remain short-lived and reveal no execution authority outside that binding.
5. Run the same trusted fixed-fixture task supervisor and test explicit running Stop, process recovery, token rotation, revoked bindings, network outages, duplicate deliveries and full-scope display on a real phone before deployment. Remote consent policy, Telegram privacy/retention choice, and production retention/account isolation need acceptance. Only the registered arithmetic fixture and opt-in disposable local Python fixture are executable today; general Mac tools, user-selected projects, model autonomy, actual personal memory/device voice integration and the VAD issue remain outside this slice.

Protocol reference: [official Telegram Bot API](https://core.telegram.org/bots/api), checked October 9, 2026. Its update delivery, callback and sendMessage contracts guide the future sender; this offline core does not claim a tested live connection.

The local-executor extension is tested with this same offline adapter by constructing a LocalTaskStore: duplicate updates preserve one task, an exact callback approves its real test/patch scope, and LocalTaskWorker executes only the registered disposable project. Permissions for a future first connection are limited to bot token access, outbound HTTPS to Telegram, one verified private user/chat binding, and the private fixture/evidence roots. No inbound port, administrator rights, full-disk access, Accessibility/Automation grants, account actions or unrelated project permissions are needed for this bounded slice.
