# Disconnected Telegram transport rehearsal

`app.task_telegram_transport.TelegramTransport` is an off-by-default delivery layer for the existing trusted-update fixture adapter. `TelegramHTTPS` provides an optional fixed HTTPS connector, but no real token, listener, webhook, automatically started loop, credential loading, production wiring, or live account binding is included. Tests inject `FakeHTTP` or `httpx.MockTransport` with synthetic placeholder tokens; no real Telegram connection has been exercised. The methods and JSON shapes implement Bot API `getUpdates`, `sendMessage`, and `answerCallbackQuery`; current live protocol compatibility remains to be verified before deployment.

Construct with an injected fixture client exposing `async call(method, payload)` or with `TelegramHTTPS`. Default `enabled=False` performs no calls. HTTPS live calls additionally require `live_authorized=True` and an explicitly configured token; constructing a connector alone never enables access. `offline_fixture=True` is a fixture marker, not a network security mechanism, and custom client injection is trusted code. No CLI or automatic setup enables live access. An owner binding must be established out of band; Telegram names and client-provided owner labels never establish access. The source adapter remains authoritative for private-chat checks, owner isolation, idempotent task actions, and exact revision/nonce/digest approval.

The HTTPS connector permits only the three fixed method names at `https://api.telegram.org`, sends JSON by POST, verifies TLS, ignores environment proxy/netrc configuration, refuses redirects, uses a 20-second Telegram long poll with a 35-second HTTPS/outer deadline (five seconds for sends), and bounds response bodies to one million bytes. Failures expose a generic exception without a token-bearing URL. Token-redaction filters cover the HTTPX/HTTPCore loggers used by this connector; caller code must never log the token or connector internals. Tests exercise the actual HTTPX request construction through in-memory MockTransport; they do not exercise DNS, TLS handshakes, Telegram reachability, token validity, or API authorization. A future production setup must protect token storage and authenticated bind/revoke administration separately.

At startup, after the previous consumer is known to be inactive, call `await service.recover()` before delivering. The durable SQLite outbox records `pending`, `sending`, `sent`, `uncertain`, and `withheld` (a stale keyboard that was never attempted). Recovery changes interrupted `sending` records to `uncertain`: the request may have reached Telegram before the process died. A timeout, cancellation, exception, or unrecognized failure similarly becomes uncertain. There is no automatic resend or operator override for uncertain messages. In particular, an uncertain scope chunk blocks the dependent approval keyboard. This provides conservative at-most-attempt behavior for ambiguous outcomes; it does not promise exactly-once Telegram delivery.

Only an explicit Bot API `429` rejection can retry delivery. Its valid `retry_after` delay (at most one day) is persisted, with at most three attempts. Invalid or excessive delivery delays fail closed as uncertain. Polling rate-limit delays are also persisted without advancing the offset. Other delivery errors remain uncertain. Ordinary outbox storage is capped at 5,000 rows, plus 128 reserved Stop-response rows. Stop admission bypasses ordinary adapter-update/outbox caps and its confirmations take delivery priority. Even if reserved confirmation space is exhausted, Stop executes and a durable decision records response backpressure. Ordinary updates encountered at capacity are not admitted as actions; a bounded decision journal records rejection before advancing the polling offset. If response expansion exceeds capacity after an idempotent action, that outcome is recorded and the core cached response is retained. Pending and uncertain delivery groups are never automatically deleted. Fully confirmed/withheld groups older than one day can retire only after their approval tokens have expired; associated cached responses retire with a persistent update floor that rejects old replays. The decision journal keeps its latest 1,000 records, while the durable offset preserves consumption history. The core's callback cap and TaskStore's own safety/retention rules remain in force. Long-lived uncertain backlog still requires deliberate offline maintenance; this slice never silently retries uncertain actions or deletes their evidence.

`await service.run(stop_event)` is an explicitly invoked scheduler: it recovers once and starts separate long-polling and outbound loops. Idle/error waits default to one second, with maximum failure backoff of 30 seconds; successful delivery drains eligible messages with a short bounded wait. Long polling holds a separate poll lock and never holds the binding/send lock, so revocation and trusted Stop ingestion remain responsive. It permits one running consumer per database within the process. A stop event or cancellation cancels and awaits the in-flight cycle; an interrupted outbound request becomes uncertain. Construction never starts this loop. No loop or live connector was started against Telegram in this work.

Polling persists the next update offset in the same transaction that stores all response parts. If a task action succeeds before enqueueing is interrupted, the source adapter's cached update response and idempotent actions permit replay. Successful response enqueue and polling offset advancement share one transaction. Malformed updates with valid update IDs and explicitly rejected/backpressured updates have durable decisions before offset advancement, so poison messages do not block later Stop requests. Unbound updates receive no private reply. Authorized invalid, expired, or early callbacks enqueue an acknowledgement and a safe error message without approving work. The acknowledgement is an attempt, not proof that Telegram accepted an old query. Delayed callback acknowledgements may expire in Telegram; no live callback UX guarantee is claimed.

Messages use plain text with previews disabled and no `parse_mode`. Splitting preserves code points and limits each chunk to 3,500 UTF-16 units. Approval buttons appear in a separate final message after every preceding scope chunk has a successful message receipt. Immediately before keyboard delivery, the service rechecks callback ownership, exact task revision/digest/nonce/expiry, and awaiting-approval state. Callback admission also requires durable successful receipts for every scope chunk and a keyboard delivery attempt under the current binding. An early or guessed callback cannot approve a scope whose delivery is incomplete or uncertain. A callback following an uncertain keyboard receipt may proceed because full scope delivery is established and the trusted callback demonstrates keyboard receipt; the source adapter still validates exact approval and expiry. Expired or changed never-attempted keyboards are withheld and automatically replaced by a fresh full-scope delivery wave with a new token. Refresh displays the latest planner metadata and retains that metadata when the source/executor remain unchanged. Each new wave has its own full-scope receipt dependencies. No replacement is attempted for an uncertain scope send. A new user approval is always required; this layer never fabricates an approval or treats mere successful delivery as user consent.

All service instances for the same resolved database share one async lock. **Every bind and revoke must use the service's async wrappers, on the same event loop and in the same process.** The lock stays held through the injected send and its durable result, so a concurrent revoke completes after an already-admitted send and blocks subsequent chunks. A revoke request cannot recall an in-flight delivery. Calling the synchronous adapter directly from another thread, another process, or another event loop bypasses this boundary. Startup recovery must not run alongside an active consumer. There is no multiprocess lease or authenticated administrative service here.

Tests exercise durable offset/restart, duplicate actions, full long-scope chunk ordering, lost replies, interrupted sends, cancellation, rate-limit delay and retry exhaustion, callback acknowledgements, expired/changed keyboards, rebind privacy, and concurrent revoke ordering with actual TaskStore state and fake HTTP. They do not establish Bot API authentication, live reachability, durable remote receipt, or genuine model planning. Native LCD and voice integration remain separate work.

Use `await TelegramTransport.create(store, http, enabled=...)` from async service setup so adapter/schema construction occurs off the event loop. The synchronous constructor and adapter API remain for synchronous offline harnesses; callers must not use them directly on an async production loop. All runtime storage, binding, adapter handling, retention, preparation and completion work runs in cancellation-drained worker threads. Read-only queries use read transactions. Cancellation does not release the async authority lock while an admitted thread operation is still running. All privileged bind/revoke calls must still use service wrappers; no thread-owned RLock spans an await.

The operational adapter supports `/help`, `/tasks`, owner-scoped status/review/questions, and `/stop` with an optional task ID. Bare Stop selects only one unambiguous active task; otherwise it lists choices. Exact scope is rendered with labelled prose, numbered command arguments, all fingerprints, restrictions, planner provenance, and expiry. Status sends step counts/exit summaries; raw executor output and artifact contents stay in local evidence by default. Bound malformed commands receive generic guidance rather than exception details or a silent failure.

At ordinary outbox saturation, callbacks can be durably rejected and consumed without an acknowledgement or error delivery. Reserved Stop admission preserves cancellation, but even its confirmation can be withheld when the reserve is exhausted. This is an explicit bounded-service limitation, not guaranteed callback UX.
